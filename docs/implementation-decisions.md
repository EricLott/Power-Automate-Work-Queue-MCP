# Local implementation decisions

These decisions implement the user's authorized local-first sequence. They do not replace the proposed architecture or close its platform gates.

1. **Runtime boundary.** A C# engine contains the lifecycle rules. `IStore` separates a serialized, durable local model from the Dataverse SDK adapter. The adapter calls native `Dequeue`; it never claims work through a list/update race. It rejects calls outside a Dataverse transaction. The actual dequeue response shape, transaction participation, and rollback remain live experiments.
2. **Data storage.** Companion tables use protected unique keys, a versioned JSON document, and scalar operations projections. Queue state remains native. A unique queue-binding registry prevents two logical queues from claiming the same physical queue and avoids full registry scans. Operational rows are team-owned; the adapter requires `OwnerTeamId` during real creation. Principal profiles are administrator-maintained configuration. The first import must confirm alternate keys, row versions, team permissions, and delete guards. Relational navigation beyond the scalar views can be refined from the first validated metadata export. The lifecycle engine always uses the initiating identity. The native admission guard alone performs narrow SYSTEM reads of queue identity/registry metadata so hidden rows cannot bypass protection; it never writes with that service and checks both old and new queue IDs on a move.
3. **Contracts.** The framework implements a bounded JSON Schema draft-07 subset and rejects unsupported keywords, remote references, malformed definitions, oversized JSON, duplicate properties, and invalid business payloads. It does not claim full draft-07 conformance. Native draft-3 envelope validation is separately supplied in `templates/native-envelope.schema.json`; breaking that immutable envelope requires a new queue.
4. **Reliability.** Source deduplication, command replay, and business idempotency are separate. Attempts snapshot policy and contract hashes. Worker identity, generation, lease, and deadline fence every lifecycle mutation. An unknown outcome requires review. The reference worker reconciles a stable business identity after a post-write failure. Poison/orphan items are quarantined so a malformed oldest item cannot block all work.
5. **Notifications.** The durable outbox has independent claims, leases, attempts, and terminal failure. Destinations are trusted keys; the email scaffold binds a configured operations address. Alert bodies contain IDs and disposition, not message content. Provider acceptance is not proof of inbox delivery. A lost provider response may still cause a duplicate external alert. Delivery failures do not create recursive alerts.
6. **Tests.** The harness persists runs, case snapshots, repeated executions, expected fields, attempt/error assertions, notification evidence, and cleanup status. Missing output or an observation deadline is inconclusive. Production test calls are denied by trusted actor configuration; the MCP live adapter additionally permits development bindings only. Cleanup deletes recorded successful-test-owned business rows and retains failed evidence. Local extraction uses a fixture provider and makes no live AI-quality claim.
7. **Retention.** The initial policy preserves a 30-day replay window. Bounded retention redacts old successful-item input and old receipt result bodies while retaining source identities and command fingerprints. Replaying a redacted receipt returns `ReplayExpired`; it cannot execute again. Review-required/active item evidence is held. Business records are not generally purged. Longer-term evidence deletion requires a separately validated retention policy.
8. **Autonomous scheduling.** Maintenance and sender scans persist cursors across bounded calls. The reference has event and scheduled parents calling one local `ProcessOne` child. A queue event is only a wake-up. The detached local worker and the installed flow coordinators do not depend on an MCP session.
9. **First import bootstrap.** Offline code cannot know tenant-assigned plug-in registrations or AI Builder prompt action metadata. The candidate includes the dependent assembly package and API definitions, with API implementation binding completed by `bootstrap_tenant.py` after the first unmanaged development import. Generated flows stay draft. The prompt action fails closed until an approved provider action is bound. Export that validated development installation before producing a production managed release. The locally generated managed ZIPs are structural candidates, not release-ready upgrades.
10. **Customer ownership.** Runtime upgrades do not regenerate customer scaffolds. The reference solution is a separate demonstration package. Scaffolding creates a new directory and stable customer-specific flow IDs. The MCP does not execute mailbox text, arbitrary assertion code, arbitrary URLs, or deletion expressions.

The MCP tools are intentionally small and bounded. Hosted multi-tenant MCP, Teams retry cards, public custom connectors, automatic repair, desktop certification, and other deferred items remain outside this build.
